# avalonia-extensions（三个渲染扩展包：TextMate 代码高亮 / RaTeX 公式 / Mermaid 图表）

三个独立的可选包，各自实现一个渲染接口（高亮是 Core 的 `ISyntaxHighlighter`，公式与图表是 `StreamMark.Avalonia` 的 `IMathRenderer` / `IDiagramRenderer`）并用一个 `IMarkdownPlugin` 把它注册进 `MarkdownPluginBuilder`：TextMate 包用 TextMateSharp 按行增量着色，RaTeX 包把 LaTeX 经 C ABI 交给 Rust 引擎排版成显示列表、再在界面线程转成 Avalonia 图元，Mermaid 包用 Mermaider 出 SVG、把 `var()`/`color-mix()` 展开成字面颜色后交给 Svg.Skia。三者都不解析 Markdown，也不持有任何视图。

**不负责：** LaTeX / 围栏语法本身的解析与 `MathBlock` / `MathInline` / `CodeBlock` 节点的产生（`core-parsing-and-model`，`src/StreamMark.Core/Parsing/BackslashMathExtension.cs:15`、`MarkdigMapper.cs:20`）；代码块与公式块、图表块的视图（`avalonia-text-rendering`，`Rendering/CodeBlockView.cs`、`Rendering/MathBlockView.cs`、`Rendering/DiagramBlockView.cs`）——本模块只提供渲染器；插件的聚合与 `FindDiagramRenderer` 分派（`avalonia-plugin-system`，`Plugins/PluginRegistry.cs:46`）；图片获取 / 缓存 / 解码（`avalonia-images`，`Images/ImagePipeline.cs:38` 定义 `ISvgRasterizer`）；RaTeX 原生库的构建、交叉编译与 NuGet 打包（`native-ratex`，`native/ratex/**`、`native/patches/0001-enclose-border-uses-current-color.patch`、`native/build.sh`）。

## State it owns
- **TextMate 每个主题一份 Registry / 语法缓存 / 颜色缓存，各自一把锁**：`TextMateSyntaxHighlighter._dark` / `_light`（懒加载，`TextMateSyntaxHighlighter.cs:22-23,33-36`）→ `ThemeContext` 的 `_registry`、`_grammars`（`ThemeContext.cs:21-23`）与 `_colors` / `_colorResolved` 按 colorId 惰性展开（第 26-27、86-91 行）。两个主题的锁互相独立，可并行。`RegistryOptions` 本身全进程共享一份（`TextMateSyntaxHighlighter.cs:19`，只读）。
- **语言名 → scope 的缓存**：`_scopeCache`（`TextMateSyntaxHighlighter.cs:24`，`ConcurrentDictionary`，同一语言名可能缓存 `null`）。
- **每个会话持有的按行语法状态**：`_lines` 里每行的 `Start` / `Newline` / `Tokens` / `EndState`（`TextMateHighlightSession.cs:31,316`），以及整块的旧文本 `_code` 与上一次的 `_result` 数组（第 30-33 行）；`Dispose` 会清空它们并丢掉 `_grammar`（第 303-310 行）。
- **冷启动超时重试**：单行 50ms 上限（第 17 行）、超长行不参与分词（`MaxLineLength = 4000`，第 20 行）、首次超时后用 1s 上限重试一次（`RetryTimeLimit`，第 23 行，调用点第 181-187 行）。`PrewarmAsync` 在后台用同样 50ms 上限跑一次空行分词以触发规则编译（`TextMateSyntaxHighlighter.cs:85-103`）。

## How to extend
- To add 一种代码语言 / 别名：先在 `LanguageAliases.Aliases` 里加"围栏名 → TextMateSharp language id"（`LanguageAliases.cs:11`，表里没有的名字会被当成 language id 或扩展名再去查一次，`TextMateSyntaxHighlighter.cs:140`）→ 再确认 `TextMateSharp.Grammars` 2.0.4 真的有这门语法（`Directory.Packages.props:18-19`）；能力边界写在 `docs/decisions.md:32`：**Kotlin 在 Grammars 包里不存在**，TOML 被有意映射到 INI（`LanguageAliases.cs:33`）→ 最后在宿主注册时预热，`new TextMatePlugin(prewarm: ["csharp", "rust"])`（`TextMatePlugin.cs:6,14`）或 `highlighter.PrewarmAsync(theme, …)`（`TextMateSyntaxHighlighter.cs:76`）。漏掉预热的症状是首个代码块首次 `Update` 卡数百毫秒（注释 `TextMateSyntaxHighlighter.cs:14-15`）；语言不存在时的症状是 `SupportsLanguage == false`，代码块按纯文本显示且完全不加载语法（`TextMateSyntaxHighlighter.cs:46-56`，测试 `TextMateHighlighterTests.cs:225` 用 `kotlin` 断言 false）。
- To add 一种图表语言：这一步**不需要改视图**——`BlockViewFactory` 只要 `FindDiagramRenderer(language)` 返回非空就把闭合的代码块换成 `DiagramBlockView`（`BlockViewFactory.cs:95`）。所以只要写一个 `IDiagramRenderer`（`CanRender` 认自己的语言名、`RenderAsync` 在后台跑、失败返回 `null`）→ `builder.AddDiagramRenderer(...)`（`Plugins/IMarkdownPlugin.cs:56`）→ 在宿主 `MarkdownServices { Plugins = [...] }` 注册（`README.md:33`）。漏掉注册的症状是代码块保持普通代码显示，不会有任何图表（`BlockViewFactory.cs:96`）；把 `CanRender` 写成大小写敏感会比较少见的围栏写法漏掉（Mermaid 自己做了 `Trim()` + `OrdinalIgnoreCase`，`MermaidDiagramRenderer.cs:27`）。若要改 Mermaid 的配色 / 字体，优先用 `MermaidDiagramRenderer.ConfigureOptions`（`MermaidDiagramRenderer.cs:21`）而不是改 `CreateOptions`（第 129 行）。
- To add 一种公式语法 / 命令（例如新的 `\xxx`、新的字体）：C# 侧**不需要改**——能力全在原生引擎里，`RaTeXEngine.Layout` 只是通道（`RaTeXEngine.cs:22-52`）。只有当原生返回的显示列表出现**新的条目类型或字段**时才需要在 C# 侧配合：在 `DisplayList` / `DisplayItem` 加字段（`DisplayList.cs:18`）并在 `RaTeXMathLayout.BuildPlan` 的 `switch (item.Type)` 加分支（`RaTeXMathLayout.cs:102`）。漏掉分支的症状是静默不画——`BuildPlan` 没有 `default` 分支，未知 `Type` 被直接忽略（协议本身就允许忽略未来类型，`DisplayList.cs:20`）。若要新增宿主主题化的默认颜色语义，走哨兵色（`RaTeXMathLayout.cs:16`）而不是给每条图元染色。
- To add 主题 / 配色：Mermaid 走 `CreateOptions`（`MermaidDiagramRenderer.cs:129`，`Fg`/`Bg`/`Accent`/`FontSize`/`Font`/`Tint`）；TextMate 走构造函数的两上主题名（`TextMateSyntaxHighlighter.cs:29`）。两条路径都不会让已经缓存的结果失效（见下方陷阱）。

## Invariants and traps
- **TextMateSharp 2.0.4 不是线程安全的**：`Registry` 用普通 `Dictionary` 存语法、`Grammar` 分词时惰性编译规则并写内部表、主题匹配缓存也会在分词中被写入 —— 因此对 Registry / Grammar / Theme 的**每一次**访问都必须持有 `ThemeContext.Gate`（注释 `ThemeContext.cs:13-18`），落地在第 44 行的 `Gate`、`TextMateSyntaxHighlighter.cs:91-95` 的预热锁与 `TextMateHighlightSession.cs:97` 的会话锁。**每个主题各一把锁**（明暗互不阻塞），共享锁或去掉锁的表现是随机的颜色错乱 / 崩溃而不是异常。
- **高亮只重算"变了的地方之后"的行**：`Update` 用公共前缀决定保留哪些完整行（`TextMateHighlightSession.cs:59-66`），纯追加时原地截断 `_lines`（第 72-76 行）；非追加编辑分词到某个完整行的结束状态与旧缓存**相同**且该换行已落在公共后缀里时提前返回，余下行连同 token 数组整体复用（只平移偏移，第 145-159 行）。因此"中间改一行不影响语法状态"的编辑只重算 1-2 行（测试 `TextMateHighlighterTests.cs:320`），而"在第 1 行开块注释"必须重算后面全部（测试第 297 行）；一旦提前结束条件写错，症状是旧颜色粘在后面没跟着变。
- **超长行与超时是"局部退化"而不是失败**：行内容超过 4000 字符不着色且**保持传入的语法状态**（`TextMateHighlightSession.cs:167-169`）；单行 50ms 超时后用 1s 重试（第 181-187 行），仍超时则 `stoppedEarly` 为真、该行结束状态沿用上一行状态（第 196-197 行注释：与 VS Code 一致，避免把半截状态带到后续行）。`TokenizeLineResult2.StoppedEarly` 在 2.0.4 里是 `internal`，所以这里靠 `Stopwatch` 计时判断，误判只会多重试一次（第 241-245 行）。
- **主题默认前景色的 colorId 恒为 1**：`Theme.CreateFromRawTheme` 先解析主主题时第一个登记的颜色就是默认前景，于是未被规则命中的片段（空白、标点）都带 id 1；`ResolveForegroundLocked` 对 `colorId <= 1` 直接返回 0（= 用调用方前景），其他 id 与 `DefaultForeground` 相等时也返回 0（`ThemeContext.cs:29,70-78,99-101`）。
- **RaTeX 默认色用哨兵色保留 `\color`**：`RaTeXMathRenderer.Layout` 总是把 `RaTeXMathLayout.DefaultColorSentinel`（`(0.0123, 0.0456, 0.0789, 1)`，`RaTeXMathLayout.cs:16`）当成默认色传给原生（`RaTeXMathRenderer.cs:53`），绘制时用 `IsSentinel` 容差 1e-4 判断"该用 foreground"（`RaTeXMathLayout.cs:255-270`），显式 `\color` / `\textcolor` 返回真实颜色从而被保留（测试 `RaTeXMathRendererTests.cs:96` 断言红色与哨兵色同时存在）。别把这个哨兵换成真实前景色——那会让 `\color` 与默认色不可区分。
- **`\fbox` / `\boxed` 边框的历史包袱**：原生补丁 `native/patches/0001-enclose-border-uses-current-color.patch` 已让边框使用默认颜色，所以 `RaTeXMathRenderer.HasUncoloredFrame` **恒返回 false**（`RaTeXMathRenderer.cs:74-76`）；但 `RaTeXMathLayout` 仍保留 `blackFramesAreDefault` 参数、`IsFrameRule` 与 `RectOp.Brush == null` 的路径（`RaTeXMathLayout.cs:28-38,133,252-253`），公开构造函数一律传 `false`（第 22-25 行）。旧注释里"边框固定黑色"的说法已经过时。
- **CJK / emoji 不是 KaTeX 字体能的**：字体名以 `CJK-` / `Emoji-` 开头时直接跳过 KaTeX 字体走系统回退（`KaTeXFonts.cs:49-50`）；系统回退先试 `FontFamily.Default` 再 `FontManager.TryMatchCharacter`（第 71-82 行），结果（含 `null`）按码点缓存，字形索引 0 视为缺字（第 52-61 行），缺字就直接跳过不画以免出豆腐块（第 25 行）。所有这些都要求 Avalonia 平台已初始化 —— 而图元只在 `Draw` 里构建（`RaTeXMathLayout.cs:56,81`），也就是界面线程首次绘制时，所以**不能**在后台线程构造 `GlyphRun`。
- **Mermaid 的 SVG 必须先展开 CSS 函数再交给 Svg.Skia**：Mermaider 0.15.1 的输出确实依赖 `color-mix(`（测试里对此有断言，`MermaidRendererTests.cs:114`），而 Svg.Skia 不支持 `color-mix()`，会画成黑色填充并丢连线（`CssColorResolver.cs:8-10`）——所以 `Render` 的顺序是 `MermaidRenderer.RenderSvg` → `ResolveSvg` → `SKSvg.FromSvg`（`MermaidDiagramRenderer.cs:67,83,89`），并且 `ResolveSvg` 之后整份文档里不应再出现 `var(` / `color-mix(`（测试 `MermaidRendererTests.cs:111`、`CssColorResolverTests.cs:36`）。混合规则：百分比归一化、预乘 alpha 在 sRGB 中插值、两者之和 <100% 时按比例降 alpha、非 sRGB 空间按 sRGB 近似（`CssColorResolver.cs:261-264,306-319`）；循环变量靠 `MaxDepth = 32` 终止（第 18、77、217 行）。变量来源只解析根 `<svg style="…">` 与 `<style>` 里的 `svg { … }` 规则（第 40-52 行），内联声明优先（第 68-70 行）。
- **Svg.Skia 版本被钉死在 5.1.1，托管依赖却被抬到 5.2.3，`Svg.Animation` 例外**：`Directory.Packages.props:21` 的集中版本写的是 `Svg.Skia 5.2.3`，`StreamMark.Mermaid.csproj:14-21` 用 `VersionOverride` 把它压回 `5.1.1`，并把 `Svg.Model` / `Svg.Custom` / `ShimSkiaSharp` / `Svg.SceneGraph` 覆盖到 `5.2.3`，`Svg.Animation` 保持 `5.1.1`。原因写在 csproj 注释与 `docs/decisions.md:30`：5.2.x 的 Svg.Skia 依赖 SkiaSharp 4 / HarfBuzzSharp 14.2，与 Avalonia 12.1.3（SkiaSharp 3.119.4 / HarfBuzzSharp 8.3.1.3）不兼容；而 5.1.1 的 `Svg.Model` 里 `TypeDescriptor` 用法会产生 IL2026，5.2.3 已修。Svg.Animation 5.2.x 依赖 SkiaSharp 4，所以不能跟着升。**把 `VersionOverride` 删掉就会拿 5.2.3 的 Svg.Skia，表现是原生 Skia 库冲突 / 崩溃，而不是编译错误。**
- **图表缓存键不含前景色 / 强调色 / 字号**：`_renderKey = $"{code.Language}\n{style.IsDark}\n{code.Code}"`（`Rendering/DiagramBlockView.cs:72`），但渲染上下文还带 `Foreground` / `Accent` / `FontSize` / `FontFamily`（第 103-104 行）。宿主若在同一个 `IsDark` 下换强调色或字号，已渲染的图表（含静态 `DiagramCache` 里的）不会重画 —— 这是本模块与视图层交界处最容易踩的坑。
- **静态图表缓存的容量淘汰不释放资源**：`DiagramCache.Add` 超容量时只 `Items.Remove` + `Order.RemoveFirst`（`Rendering/DiagramBlockView.cs:275-279`），没有调用 `DiagramResult.Dispose`，而 `SkiaPictureDiagram` 的 `SKPicture` / `SKSvg` 只由 `PictureHandle.Release` 释放（`SkiaPictureDiagram.cs:74-87`，没有终结器）—— 淘汰后的原生图元要等所有绘制操作也释放（`PictureDrawOperation.Dispose`，第 142 行）才可能归零，静态缓存本身不再持有引用。**这一条我只从代码读出，没有实测泄漏**：(unverified)。
- **`Draw` 可能晚于 `Dispose`**：自定义绘制操作在渲染线程执行，`PictureHandle` 因此做引用计数，`DiagramResult` 或场景里的绘制操作谁是最后一个持有者谁负责释放（`SkiaPictureDiagram.cs:15-18,45,50`）；`Dispose` 幂等（`Dispose` 里 `Interlocked.Exchange` 再 `Release`，测试 `MermaidRendererTests.cs:208`）。
- **三个插件的实例语义不一致**：`RaTeXPlugin` 默认共享 `RaTeXMathRenderer.Shared`（`RaTeXPlugin.cs:10`，因此缓存与 `Clear()` 是进程级的，测试 `PluginSystemTests.cs:166` 就依赖这一点），`TextMatePlugin` 与 `MermaidPlugin` 每次新建（`TextMatePlugin.cs:10`、`MermaidPlugin.cs:10`）—— 后者意味着多份 `MarkdownServices` 会各自加载一遍语法、各自渲染同一张图表（只有视图侧静态缓存能省掉一部分）。
- **`MermaidDiagramRenderer` 只认 `mermaid`**：`CanRender` 对 `mmd`、`null`、空串都返回 false（`MermaidDiagramRenderer.cs:27-28`，测试 `MermaidRendererTests.cs:104`），`BlockViewFactory` 因此把它当普通代码块；图表块也只在**代码块闭合后**才创建（`BlockViewFactory.cs:94-95`，`AddDiagramRenderer` 的文档注释同样强调，`Plugins/IMarkdownPlugin.cs:55`）。
